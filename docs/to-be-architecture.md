# To-Be архитектура системы «Кинобездна» (CinemaAbyss)

## Диаграмма контейнеров (C4, level 2)

Система разделена на домены (Movies, Events, Users, Payments, Subscriptions), развёрнута в Kubernetes,
единая точка вызова — API Gateway (proxy-сервис, паттерн Strangler Fig).
Асинхронное интеграционное взаимодействие между доменами построено на Kafka.

Диаграмма контейнеров в нотации С4 (PlantUML): **[schemas/containers.puml](schemas/containers.puml)**,

![Диаграмма контейнеров ](schemas/containers.svg)

## Описание решения

### Домены

| Домен | Контейнер (To-Be) | Статус миграции |
|---|---|---|
| Movies (метаданные фильмов, жанры, рейтинги) | movies-service (Go) | Вынесен из монолита |
| Events (событийное взаимодействие) | events-service (Python + Kafka) | Новый сервис, MVP |
| Users (пользователи, аутентификация) | монолит -> user-service | Следующий кандидат на выделение |
| Payments (платежи, скидки) | монолит -> payment-service | Планируется |
| Subscriptions (подписки) | монолит -> subscription-service | Планируется |

### Ключевые архитектурные решения

1. **Единая точка вызова — API Gateway (proxy-service).** Все клиенты обращаются к системе только
   через Ingress -> proxy-service. Это позволяет менять внутреннюю топологию сервисов незаметно
   для пользователей — требование перехода без простоя.
2. **Strangler Fig.** Прокси постепенно переключает трафик домена Movies с монолита на
   микросервис через фиче-флаг `GRADUAL_MIGRATION` и процент `MOVIES_MIGRATION_PERCENT`
   (0% -> 100%). Тот же механизм будет использован для доменов Users/Payments/Subscriptions.
3. **Событийная интеграция через Kafka.** events-service — MVP, проверяющий гипотезу: события
   User/Payment/Movie публикуются в топики `user-events`, `payment-events`, `movie-events`
   и обрабатываются consumer'ом. Далее на Kafka переводится интеграция с рекомендательной
   системой (замена RabbitMQ) и межсервисное взаимодействие.
4. **Kubernetes + Helm.** Все контейнеры развёрнуты в кластере Kubernetes, деплой описан
   Helm-чартом, что даёт масштабирование, самовосстановление и повторяемые релизы.
5. **CI/CD (GitHub Actions).** Сборка образов в GitHub Container Registry и автоматический
   прогон API-тестов на каждый коммит.
6. **База данных.** На переходном этапе PostgreSQL остаётся общей; по мере выделения сервисов
   каждый домен получает собственную схему/БД (database-per-service).
